# Sixth-run prompt payload audit

This audit measures the original private PromptSnapshots, not the redacted public strings. The [measured JSON](native-run-rmulp44n21-prompt-audit.json) identifies the raw receipt hash. Character shares describe message content; they are **not exact tokenizer attribution** or predicted latency savings. Original records remain unchanged.

Across 16 main requests, 780,125 message characters comprised 75.7% conversation, 10.9% standing instructions, 7.2% tool catalogue, 4.9% fresh context, and 1.3% response contract. The identical 8,817-character system prefix repeated each time; reported cached tokens were zero. Repeated source receipts occupied 197,956 characters (25.4%), mostly `app/page.js` and CSS.

Check plans appear in accepted assistant actions, are echoed again in observations, and appear a third time inside complete check receipts. Across retained input history there were 34 assistant plan copies, 44 check receipts, and 44 echoed check calls. Plan arrays in assistant actions occupied 84,886 characters, echoed calls 112,056, and arrays inside receipts 109,856: together 39.3% of main message content. These count repeated appearances across snapshots, including inherited history, not distinct executions.

Seven model attempts repeated an already-failed plan unchanged. They consumed 105,321 reported input tokens, 4,375 output tokens, and 530.59 provider seconds, excluding tool time. This is observed wasted recovery effort, not a guaranteed saving: a correct diagnosis still costs inference and execution. The existing job already prohibited unchanged failing plans. Typed failure status and actual-versus-expected diagnostics should precede further prompt prohibitions.

The three successful compactor calls consumed another 43,067 input tokens and 260.41 provider seconds. Their summaries were already only 986–1,612 characters. Lowering the compaction threshold blindly can add expensive model calls without addressing duplicated recent observations.

The first scoped change should keep complete immutable check proof and exact call/observation events, while giving the model a compact check receipt: status, artifact/build/revision identity, completed and total step counts, interaction mode, timing, and a stable evidence reference. On failure, preserve error/reason and the first incomplete step's index/action/selector/expected value, with captured-native actual text or missing-element diagnostics when available. An incomplete step is not proof that its action never ran; timeouts can occur after an action. A precondition/storage/runtime failure must not be mislabeled as a text assertion failure.

Opt-in observation formatting can refer to ordered stage/call identities rather than repeating the full arguments already present in the assistant action. Same-name concurrent calls must keep separate identities. Neither success nor failure should be cached merely because arguments repeat. The implementation now retains full frozen call and observation events in a separate persisted run record; the bounded UI log and latest artifact check view are not its evidence archive.

An offline replay through the new check validator/projector and `staged-v1` serializer accepted all nine original check receipts. Their observation blocks decreased from 56,599 to 6,019 JavaScript string characters (89.37%). The eight failed projections retain the first incomplete step and its recorded diagnostic; the successful projection retains the artifact/build/revision, 37 completed steps, and 20 outcome assertions. Full raw receipts remain unchanged. This figure covers these nine observation blocks only: it excludes assistant plans, generic-result JSON escaping, later repeated appearances, extra format instructions, and tokenization. It is not a measured model reliability or latency improvement. Existing persisted observations are not rewritten; the opt-in format applies to future tool results.

Smaller configuration changes are secondary. The generic soul is 1,821 characters per request (3.7% of aggregate main input); unused board/memory grants account for roughly 1,011 catalogue characters per request (about 2.1%). Removing them from a deliberately scoped coding profile may help, but does not address the dominant duplicated history. No new model or browser performance claim follows from this offline audit.
