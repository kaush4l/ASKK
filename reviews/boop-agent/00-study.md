# 00 — Study: boop-agent

Descriptive study of [raroque/boop-agent](https://github.com/raroque/boop-agent)
(v0.2.0, commit 3197913, 2026-07-13, MIT, TypeScript). A "text-an-agent"
personal proactive agent: the user texts it over iMessage; it dispatches
LLM sub-agents that touch Gmail/Slack/calendar/browser and texts back.
All file:line cites verified against that commit. This document is study
only — reviews and the browser mapping live in the sibling docs 01–07.

## 1. Where does the app run?

**A long-running Node ≥20 daemon on the user's machine** (`package.json:125`
`"engines": { "node": ">=20" }`), executed directly from TypeScript via
`tsx` (`package.json:30` `"start": "npm run preflight && tsx server/index.ts"`).
The LLM itself is external — Anthropic or OpenAI infrastructure — but every
line of application logic runs in this one Node process.

### 1.1 The server process

`server/index.ts:35-221` (`main()`) is the whole boot sequence:

- Express app + Node `http` server + `ws` WebSocketServer on one port,
  default **:3456** (`server/index.ts:190-201`). Routes: `/health`, `/chat`,
  `/runtime-config`, `/sendblue`, `/composio`, `/memory`, `/browser`,
  `/apple`, `/changelog`, `/agents/:id/{cancel,retry}`, `/consolidate`,
  and `WS /ws` (`server/index.ts:74-199`).
- A trust gate runs before everything: requests that are neither public-server
  routes nor trusted-local get a 404 (`server/index.ts:59-65`,
  `server/local-access.ts`). The WS endpoint accepts local connections only
  (`server/index.ts:192-196`).

### 1.2 "Proactive" = in-process timers + one inbound webhook

All background behavior is `setInterval` loops started at boot
(`server/index.ts:37-45`), plus one push channel:

| Loop | Interval | Source |
|---|---|---|
| Automation scheduler — polls Convex for due cron automations, fires each as an execution agent | 30 s | `server/automations.ts:123` |
| Heartbeat — kills live agents stuck >15 min, marks orphaned rows failed after 90 s | 60 s | `server/heartbeat.ts:6-7,37` |
| Memory cleanup — decay-score, archive <0.15, prune <0.05 | 6 h | `server/memory/clean.ts:5-6,84` |
| Memory consolidation — proposer → adversary → judge pipeline | 24 h | `server/consolidation.ts:481` |
| Image GC — deletes old Convex `_storage` images | 12 h | `server/images/clean.ts:5,171` |

Cron parsing/next-run computation is `croner` (`package.json:49`);
`nextRunAt` is stored back into Convex, so "scheduling" is a poll against
DB state, not OS cron.

The push channel is a **Composio webhook**: boot registers a
`GMAIL_NEW_GMAIL_MESSAGE` trigger subscription against a public URL
(`server/index.ts:51-56`, `server/composio-webhook.ts:103-138`,
`server/proactive-email.ts:18`). Inbound emails are HMAC-verified
(`server/composio-routes.ts:199-233`), run through an LLM importance
rubric (`server/proactive-email.ts:86`), and important ones become a
synthetic "proactive" turn that texts the user (`server/proactive-email.ts:4,12`).

Because the timers are in-process, the daemon must stay up for the agent
to be proactive — and must stay **single-instance**: ARCHITECTURE.md:258
states it plainly: "The automation loop runs in-process. If you deploy
multiple instances, you'll double-fire."

### 1.3 Two swappable LLM runtimes

`server/runtimes/index.ts` dispatches on a runtime config (`claude` |
`codex`) stored in Convex `settings` and switchable mid-conversation by
texting "switch to codex" (`server/interaction-agent.ts:263-274`,
`convex/schema.ts:227-231`):

- **Claude** — `query()` from `@anthropic-ai/claude-agent-sdk`
  (`server/runtimes/claude.ts:77`), i.e. the Agent SDK's local agent
  harness, with `permissionMode: "bypassPermissions"`
  (`server/runtimes/claude.ts:86`). In-process tools are exposed as SDK
  MCP servers via `createSdkMcpServer` (`server/runtimes/claude.ts:32-52`).
- **Codex** — spawns a `codex app-server` **child process** and speaks
  JSON-RPC over stdio (`server/runtimes/codex-app-server.ts:1`), against
  6.3k lines of generated protocol types
  (`server/runtimes/codex-app-server-protocol/`, regenerated by
  `npm run codex:protocol`, `package.json:29`). It reuses the user's local
  `~/.codex/auth.json` login, copied into a temp CODEX_HOME per run
  (`server/runtimes/codex-app-server.ts:62-71`) — subscription billing,
  tracked as `billingMode: "codex-subscription"` (`convex/schema.ts:74`).

So LLM inference is always external (API or subscription backend), but
tool execution — MCP tools, browser control, Apple data reads — happens
inside the local Node process.

### 1.4 Dev and desktop topology

`npm run dev` = `scripts/dev.mjs` (445 lines), which spawns four child
processes (`scripts/dev.mjs:2,127`):

1. `tsx watch server/index.ts` — the daemon
2. `convex dev` — Convex function sync + codegen
3. `vite` — the debug dashboard SPA on :5173 (`README.md:236`)
4. `ngrok` — public tunnel so Sendblue/Composio webhooks can reach
   localhost (`scripts/dev.mjs:234-244`; skipped when a static
   `PUBLIC_URL` is set, `scripts/dev.mjs:41-45`)

The optional **Electron app** (`electron/main.cjs`, 844 lines) is a
packaging shell, not a different architecture: it copies the project into
`~/Library/Application Support/Boop/runtime`, then spawns the same `tsx`
server as a child process with a status window
(`electron/main.cjs:148-156,238-248`; `README.md:201`).

## 2. Where is state stored?

### 2.1 Convex is the single source of truth

A **hosted realtime database** (convex.dev). Every durable fact lives in
13 tables defined in `convex/schema.ts` (249 lines):

| Table | Role | Cite |
|---|---|---|
| `messages` | full chat transcript, role user/assistant/system, optional image `_storage` ids | `convex/schema.ts:5-17` |
| `conversations` | per-thread metadata (title, summary, counts) | `convex/schema.ts:19-25` |
| `memoryRecords` | the memory store: `tier` short/long/permanent, 7 `segment`s (identity, preference, correction, relationship, project, knowledge, context), `importance`, `decayRate`, `accessCount`, `lifecycle`, `supersedes`, plus a **1024-dim vector index** filtered by lifecycle | `convex/schema.ts:27-64` |
| `executionAgents` | one row per spawned sub-agent: task, status, tokens, cost | `convex/schema.ts:66-96` |
| `usageRecords` | append-only LLM cost log, one row per model call by source (dispatcher / execution / extract / consolidation-{proposer,adversary,judge} / proactive) | `convex/schema.ts:101-128` |
| `agentLogs` | per-agent audit trail (thinking / tool_use / tool_result / text / error) | `convex/schema.ts:130-146` |
| `memoryEvents` | append-only event log for the dashboard | `convex/schema.ts:148-157` |
| `automations` + `automationRuns` | cron definitions (with pinned IANA timezone) and their run history | `convex/schema.ts:159-178,233-248` |
| `sendblueDedup` | webhook dedup by `message_handle` | `convex/schema.ts:180-183` |
| `drafts` | staged external actions: pending/sent/rejected/expired | `convex/schema.ts:185-201` |
| `consolidationRuns` | consolidation history incl. full reasoning JSON | `convex/schema.ts:203-222` |
| `settings` | runtime overrides — model, runtime provider, browser flags, webhook secrets — "use opus via iMessage without a redeploy" | `convex/schema.ts:224-231` |

MMS images are stored in Convex `_storage` and referenced by id from
`messages` and `memoryRecords` (`convex/schema.ts:12,54`).

### 2.2 Local filesystem state (machine-bound)

- **Embedding model cache** — when no `VOYAGE_API_KEY`/`OPENAI_API_KEY` is
  set, memory embeddings run locally via `@huggingface/transformers`
  with `Xenova/bge-large-en-v1.5`, a ~1.3 GB download cached on disk
  (`server/embeddings.ts:17-19,34-35,88`). All three providers produce
  1024-dim vectors to match the Convex vector index
  (`server/embeddings.ts:3,18`).
- **Patchright Chrome profile** — the opt-in local-browser integration
  keeps a persistent Chrome profile dir; cookies/sessions live there,
  never in Convex (`server/browser/launcher.ts:32`; ARCHITECTURE.md:187).
- **`.env.local` secrets** — Sendblue keys, Composio key, provider keys
  (`server/sendblue.ts:56-57`; ARCHITECTURE.md:156-157). For the packaged
  app these live under `~/Library/Application Support/Boop/runtime`
  (`README.md:201`).
- **Codex auth** — `~/.codex/auth.json`, reused per run
  (`server/runtimes/codex-app-server.ts:62-71`).

Memory intelligence is code + Convex, not model state: post-turn
extraction is fire-and-forget (`server/interaction-agent.ts:642-651`,
`server/memory/extract.ts`), decay is
`importance × max(0, 1 − decayRate × daysSinceAccess) × (1 + log(1+accessCount)×0.1)`
(`server/memory/clean.ts:34`, ARCHITECTURE.md:70-72), and daily
consolidation is a three-role adversarial LLM pipeline — proposer
suggests merge/supersede/prune, adversary attacks each proposal, judge
rules (`server/consolidation.ts:12,41,69,242-362`).

## 3. How does it work across devices?

**It has no sync protocol of its own. Its multi-device story is "your
phone is a messaging client and the database is hosted."**

- The user's primary "device" is **any device with iMessage** — the
  Sendblue bridge turns a paid third-party iMessage API into the app's
  front door and back channel. Inbound: Sendblue POSTs to
  `/sendblue/webhook`, deduped via the `sendblueDedup` table
  (`server/sendblue.ts:232-245`). Outbound: `sendImessage()` strips
  markdown and chunks replies to 2900 chars (`server/sendblue.ts:12,77-93`).
  iMessage's own cross-device sync (phone/laptop/tablet) is what the user
  experiences as "works everywhere."
- The **debug dashboard** (React/Vite SPA, ~11k lines under `debug/`) is
  a read-mostly second surface: it subscribes to Convex reactive queries,
  so any browser pointed at it sees live state without polling
  (ARCHITECTURE.md:251). Control actions go through the local HTTP API
  and a local-only WebSocket for streaming events
  (`server/broadcast.ts`, `server/index.ts:191-199`).
- The **host is pinned to one machine**. State would survive moving the
  daemon (Convex is hosted), but only one instance may run at a time —
  the in-process schedulers double-fire otherwise (ARCHITECTURE.md:258) —
  and the local browser profile, Apple-data readers (Full Disk Access,
  `server/apple/`), embedding cache, and `.env.local` are all
  machine-bound.

So: **state is multi-device (hosted Convex + iMessage), the application
is single-host.**

## 4. Message flow

```mermaid
sequenceDiagram
    participant U as User (iMessage)
    participant SB as Sendblue
    participant S as sendblue.ts
    participant IA as Interaction agent (dispatcher)
    participant EA as Execution agent (per task)
    participant T as Composio / browser / apple tools
    participant CX as Convex

    U->>SB: text
    SB->>S: POST /sendblue/webhook
    S->>CX: dedup by message_handle
    S->>IA: handleUserMessage()
    IA->>CX: save user msg + fetch last 10 turns
    IA->>CX: recall() memories (vector search)
    IA-->>U: send_ack ("On it — one sec")
    IA->>EA: spawn_agent(task, integrations[])
    EA->>T: WebSearch / toolkit MCP calls
    EA->>CX: agentLogs (every tool_use/result)
    EA->>CX: save_draft (external actions staged, never sent)
    EA-->>IA: result string
    IA->>SB: final reply, chunked ≤2900 chars
    SB->>U: iMessage
    IA->>CX: persist assistant msg + usageRecords
    Note over IA,CX: background: extract.ts writes memories (fire-and-forget)
    Note over CX: later: clean.ts decays/archives; consolidation.ts merges daily
```

Draft gate: execution agents can only `save_draft`; the send tools are
reachable solely through the dispatcher's `send_draft`, which spawns a
fresh execution agent with the stored payload (`server/execution-agent.ts:104-106`,
ARCHITECTURE.md:99-101).

## 7. Patterns worth noting

- **Dispatcher/executor split with per-spawn tool scoping.** The
  interaction agent has a tiny fixed toolset and an explicit
  `disallowedTools` list blocking every SDK built-in
  (`server/interaction-agent.ts:558-569`); it cannot touch the world.
  Each execution agent gets only the integrations named in its spawn
  call, and each Composio toolkit becomes a fresh session scoped to that
  one toolkit (`server/execution-agent.ts:156-175`, ARCHITECTURE.md:139-146).
- **Draft-before-send gate.** All externally visible actions are staged
  as `drafts` rows; the only commit path is the dispatcher's
  `send_draft`, so the human-facing agent is the gatekeeper
  (`server/execution-agent.ts:104-106`).
- **Memory as tiers/segments/decay + adversarial consolidation.**
  Explicit `write_memory` + inferred extraction, scored decay with
  reinforcement, and a daily proposer→adversary→judge debate whose full
  reasoning is persisted per run (`server/consolidation.ts`,
  `convex/schema.ts:203-222`).
- **Append-only observability.** `usageRecords`, `agentLogs`,
  `memoryEvents` are insert-only tables; the dashboard is a pure reader.
  Cost is attributed per call-site source (`convex/schema.ts:98-128`).
- **Settings-table-over-env.** Anything a user might want to change from
  their phone (model, runtime, timezone, browser flags) is a Convex
  `settings` row read at runtime, with env as fallback only
  (`convex/schema.ts:224-231`, ARCHITECTURE.md:167-169).
- **UX affordances for a texting medium:** mandatory `send_ack` before
  slow spawns (`server/interaction-agent.ts:61-71`), phone-number
  redaction on every outbound path (`server/interaction-agent.ts:590`),
  placeholder-reply detection with a human fallback
  (`server/interaction-agent.ts:594-602`).
